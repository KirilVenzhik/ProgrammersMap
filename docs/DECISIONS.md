# Журнал решений (ADR)

Формат: `## ADR-N: Название` → Контекст / Решение / Последствия. Новые записи — в конец.

## ADR-1: Razor Pages вместо SPA
Контекст: главный канал трафика — SEO, страница на каждую тему.
Решение: серверный рендеринг Razor Pages, JS только для прогресса.
Последствия: просто, быстро индексируется; интерактив ограничен — достаточно для чеклиста.

## ADR-2: Темы в JSON, а не в БД (фазы 1–2)
Контекст: контент меняется редко, правится через git.
Решение: `content/topics.json` как источник правды, загрузка в память при старте.
Последствия: БД не нужна до появления аккаунтов. `slug` — стабильный ID.

## ADR-3: Разделение моделей Opus/Sonnet
Решение: Opus планирует и проверяет, Sonnet (`implementer`) пишет код, Opus (`reviewer`) ревьюит.
Последствия: дешевле, чем всё на Opus; контроль качества через независимое ревью.

## ADR-4: Slug'и сгенерированы транслитом
Контекст: slug'и в topics.json сделаны автоматически из русских названий.
Решение: до релиза фазы 1 Opus может один раз их почистить (задача P1-01). После релиза — менять только с редиректом.

## ADR-5: Тестовые пакеты и формат решения
Контекст: ARCHITECTURE.md задаёт xUnit и `WebApplicationFactory`; CONVENTIONS требует ADR на NuGet-пакеты. .NET 10 по умолчанию создаёт `.slnx`.
Решение: в тестовых проектах — `Microsoft.NET.Test.Sdk`, `xunit`, `xunit.runner.visualstudio`, `coverlet.collector` (шаблон `dotnet new xunit`); в Web.Tests дополнительно `Microsoft.AspNetCore.Mvc.Testing`. Версии — из шаблона SDK / актуальные стабильные, задаются в csproj. Решение — классический `ProgChecklist.sln` (`--format sln`), как в BACKLOG.
Последствия: другие пакеты по-прежнему только через новый ADR.

## ADR-6: Расположение topics.json во время работы приложения
Контекст: источник правды — `content/topics.json` в корне репо, а ContentRoot Web-проекта — `src/ProgChecklist.Web`. Путь должен работать при `dotnet run`, в тестах (`WebApplicationFactory`) и после publish.
Решение: Web.csproj копирует файл в output/publish как `content/topics.json` (ссылка, без дублирования в git). Путь задаётся в конфигурации `Content:TopicsPath` (по умолчанию `content/topics.json`); относительный путь разрешается от `AppContext.BaseDirectory`. Каталог загружается один раз при старте (fail fast) и регистрируется как singleton `ITopicCatalog`.
Последствия: битый или отсутствующий JSON роняет приложение при старте, а не на первом запросе. Подмена пути — через appsettings/переменную окружения `Content__TopicsPath`.

## ADR-7: Английские slug'и
Контекст: транслит-slug'и из ADR-4 длинные (до 60 символов), часть обрезана посреди слова, читаются плохо. Сайт ещё не выпущен — прогресса пользователей и внешних ссылок нет.
Решение: в P1-01 заменить все slug'и (разделы, группы, темы) на короткие английские: латиница в нижнем регистре, цифры, дефис; ≤ 40 символов; общепринятые термины (`join`, `sql-injection`, `big-o`). Уникальность — как в P0-02 (разделы глобально, группы и темы — внутри раздела). Формат закрепляется тестом.
Последствия: URL короче и стабильнее; русские ключевые слова для SEO — в `<title>`, `h1` и description, а не в URL. После релиза slug'и меняются только с редиректом (ADR-4 в силе).

## ADR-8: Базовый URL сайта для canonical, Open Graph и sitemap
Контекст: canonical, `og:url`, `sitemap.xml` и `robots.txt` требуют абсолютных URL, а домена пока нет (P5, `needs-human`). Брать хост из запроса небезопасно в проде: заголовок `Host` подделывается, а с `AllowedHosts: "*"` это прямой путь к отравлению кэша.
Решение: конфигурация `Site:BaseUrl` (например `https://example.ru`; завершающий `/` допускается и отбрасывается). Если значение задано — все абсолютные URL строятся только от него. Если пусто (локальная разработка, тесты) — fallback на схему и хост текущего запроса. Значение валидируется при старте: абсолютный http/https URI без пути (кроме `/`), query, fragment и userinfo, иначе приложение не стартует. SEO-тексты (description) генерируются в Core из данных каталога; разметка — в layout по ViewData.
Последствия: при деплое (P5) человек обязан задать `Site__BaseUrl` и сузить `AllowedHosts`. До этого canonical локально указывает на localhost — это нормально.

## ADR-9: Локальные тесты через WSL при включённом Smart App Control
Контекст: на машине разработки включён Windows Smart App Control. Он блокирует свежесобранные неподписанные DLL проекта (`FileLoadException 0x800711C7`), из-за чего `dotnet test` на Windows падает нестабильно. Выключение SAC необратимо и остаётся решением человека.
Решение: `scripts/test-wsl.ps1` запускает `scripts/test-wsl.sh` в WSL (Ubuntu): .NET SDK в `~/.dotnet` пользователя WSL, артефакты сборки — в `~/.cache/progchecklist/artifacts` (Linux FS), Windows `bin/obj` не трогаются. Без `libicu` в WSL скрипт включает invariant globalization (код каталога сравнивает slug'и ординально, на результат тестов не влияет). Полная проверка — CI на windows-latest и ubuntu-latest.
Последствия: если `dotnet test` на Windows падает с 0x800711C7 — использовать `.\scripts\test-wsl.ps1`; критерий «зелёные тесты» выполняется этим прогоном. Запуск сайта — `.\scripts\run-wsl.ps1` (WSL 2 пробрасывает `localhost:5043` в Windows-браузер). Когда SAC выключат или блокировка пропадёт — снова обычный `dotnet test`.

## ADR-10: Markdig для уроков в Markdown
Контекст: в P2 у темы появляется урок в Markdown. Нужен надёжный рендер в HTML; писать свой парсер — неоправданно.
Решение: NuGet-пакет `Markdig` (BSD-2, без зависимостей, de facto стандарт в .NET), версия — актуальная стабильная, только в `ProgChecklist.Core` (это не ASP.NET-зависимость, ADR-1/Core остаётся чистым). Пайплайн: pipe-таблицы, emphasis extras, task lists, auto-identifiers для заголовков; **сырой HTML отключён** (`DisableHtml`). Рендер выполняется один раз при старте, HTML кешируется в памяти.
Последствия: вывод урока на странице — единственное место кроме JSON-LD с `Html.Raw`; безопасность держится на `DisableHtml` и на том, что контент приходит из репозитория через ревью. Пользовательский контент через этот путь не пускать никогда.

## ADR-11: Раскладка контента тем: уроки и ресурсы
Контекст: P2 — «у темы может быть markdown-файл контента и список ресурсов». `topics.json` — каталог (структура и slug'и), смешивать с ним контент не хочется: он будет расти и меняться чаще.
Решение:
- Урок: `content/lessons/{sectionSlug}/{topicSlug}.md`. Необязателен. Заголовки внутри начинаются с `##` (h1 — заголовок страницы). Файл без соответствующей темы в каталоге — ошибка старта (fail fast, как ADR-6).
- Ресурсы «Где изучить»: один файл `content/resources.json`: `{ "version": 1, "resources": { "{section}/{topic}": [ { "title", "url", "kind", "lang", "free", "affiliate" } ] } }`. `kind`: `docs|article|video|course|book|practice`; `lang`: `ru|en`; `url` — только `https://`. Неизвестный ключ темы, пустой title, не-https URL, неизвестный kind/lang, дубликат URL внутри темы — ошибка старта.
- Партнёрские ссылки (`affiliate: true`) выводятся с `rel="sponsored noopener"` и пометкой «партнёрская ссылка»; остальные внешние — `rel="noopener"`. Выбор партнёров и реальные реферальные ссылки — только человек (`needs-human`).
- Пути — из конфигурации `Content:LessonsPath`, `Content:ResourcesPath` (по умолчанию `content/lessons`, `content/resources.json`), разрешение относительно `AppContext.BaseDirectory`, файлы копируются в output/publish как `topics.json`.
- Дополнение (P2-06): неизвестное поле в записи ресурса или в корне файла — ошибка старта (опечатка `afiliate` не должна молча давать `affiliate: false`). Значения `kind`/`lang` пишутся в нижнем регистре (парсер прощает регистр, но руководство требует нижний). `free` по умолчанию `true`, `affiliate` — `false`. Ссылки, отличающиеся только `#fragment`, считаются дубликатами внутри темы. Файл урока с расширением `.md` в другом регистре (`.MD`) — ошибка старта на всех ОС (на Windows поиск файлов нечувствителен к регистру, на Linux — чувствителен).
Последствия: YAML/front matter не нужен (нет второго пакета). Контент правится через git и проходит ту же валидацию в тестах и CI. Правила для авторов — `docs/CONTENT.md`.

## ADR-12: Слой данных: PostgreSQL + EF Core в проекте ProgChecklist.Data
Контекст: P3 — аккаунты и прогресс на сервере. ARCHITECTURE заранее выбрал PostgreSQL + EF Core и проект `ProgChecklist.Data`. Нужно решить пакеты, миграции, конфигурацию и как тестировать без живой БД (локальные тесты идут через WSL, ADR-9; windows-latest в CI не запускает Linux-контейнеры).
Решение:
- Проект `src/ProgChecklist.Data` (ссылается на Core; Web ссылается на Data). `AppDbContext : IdentityDbContext<AppUser>`, сущность `UserTopicProgress(UserId, TopicKey, CompletedAt)`, PK `(UserId, TopicKey)`, FK на пользователя с каскадным удалением, `TopicKey` ≤ 100 символов, `CompletedAt` — `DateTimeOffset` (UTC).
- Пакеты: в Data — `Microsoft.EntityFrameworkCore`, `Npgsql.EntityFrameworkCore.PostgreSQL`, `Microsoft.AspNetCore.Identity.EntityFrameworkCore` (+ `FrameworkReference Microsoft.AspNetCore.App`); в Web — `Microsoft.EntityFrameworkCore.Design` (только design-time, `PrivateAssets=all`); в `tests/` — `Microsoft.EntityFrameworkCore.Sqlite`. Версии — актуальные стабильные под .NET 10, согласованные между собой. `dotnet-ef` — локальный инструмент (`.config/dotnet-tools.json`).
- Миграции — в Data, генерируются `dotnet ef`, коммитятся. Применение: `Database:MigrateOnStartup` (true в `appsettings.Development.json`, false по умолчанию); в проде — шаг деплоя (P5).
- Строка подключения `ConnectionStrings:Default` обязательна во всех окружениях: пусто → ошибка старта (fail fast, как ADR-6). Задаётся через user-secrets или переменную окружения `ConnectionStrings__Default`; в репозитории паролей нет.
- Локальная БД: `compose.yaml` с `postgres` (мажорная версия зафиксирована), пароль из `.env` (в `.gitignore`; в репо — `.env.example` с плейсхолдерами). `scripts/run-wsl.sh` собирает строку подключения из `.env`, если она не задана.
- Тесты: общий `WebApplicationFactory` подменяет провайдер на SQLite in-memory (открытое соединение на фабрику, `EnsureCreated`). Тесты, которым нужен настоящий Postgres (миграции, ограничения), помечены атрибутом `PostgresFact`: он сам ставит `Skip`, если нет переменной `PROGCHECKLIST_TEST_POSTGRES` (строка подключения). В CI ubuntu-job поднимает service-контейнер `postgres` и задаёт переменную; на windows-job и локально эти тесты пропускаются (видно в отчёте как skipped, а не как passed).
Последствия: SQLite не ловит особенности Postgres — поэтому миграции и запросы прогресса дополнительно гоняются на Postgres в CI. Запуск сайта локально теперь требует Docker (Docker Desktop с интеграцией WSL уже установлен). Каталог тем остаётся в JSON (ADR-2): в БД хранятся только ключи `"{section}/{topic}"`, поэтому slug'и по-прежнему нельзя менять без миграции данных.

## ADR-13: Аккаунты: ASP.NET Core Identity со своими страницами
Контекст: нужен вход по email и паролю. Стандартный `Microsoft.AspNetCore.Identity.UI` тянет Bootstrap и свою вёрстку, которая не совпадает с прототипом; подтверждение email и сброс пароля требуют почтового сервиса (регистрация в сервисе = человек).
Решение:
- `AddIdentityCore<AppUser>` + `AddSignInManager` + EF-хранилище из ADR-12, cookie-аутентификация. Пакет Identity.UI не используем: свои Razor Pages `/account/register`, `/account/login`, `/account/logout` (POST), `/account` в стиле сайта.
- Пароль: минимум 8 символов, без обязательных классов символов (рекомендации NIST), уникальный email. Блокировка: 5 неудачных попыток → 15 минут, включена и для новых пользователей.
- Cookie: `HttpOnly`, `SecurePolicy=SameAsRequest` (локально http; в P5 — `Always`), `SameSite=Lax`, срок 30 дней со sliding expiration, «Запомнить меня» на входе. Для путей `/api/*` — 401/403 вместо редиректа на страницу входа.
- `returnUrl` принимается только локальный (`Url.IsLocalUrl`), иначе — `/`. Все формы с antiforgery.
- Подтверждение email отключено (`RequireConfirmedAccount=false`) до появления почтового сервиса; сброс пароля и внешние входы (GitHub, Яндекс, Google) — отдельные `needs-human` задачи.
- Страницы аккаунта и `/api/*` — `noindex`, не попадают в sitemap.
Последствия: можно зарегистрироваться на чужой email (без подтверждения) — приемлемо, пока аккаунт хранит только прогресс. Перед публичным запуском (P5) нужны почта, политика конфиденциальности и решение по хранению персональных данных граждан РФ (152-ФЗ требует локализации БД в РФ — влияет на выбор хостинга).

## ADR-14: Синхронизация прогресса
Контекст: в P1–P2 прогресс живёт в localStorage (`prog-checklist-v2`). ARCHITECTURE: «при входе localStorage сливается с сервером (объединение)». Чистое объединение при каждой загрузке воскрешает снятые галочки: сняли на ноутбуке — телефон с устаревшим localStorage вернёт её при следующем слиянии.
Решение:
- API (минимальные эндпоинты, только для вошедших; иначе 401):
  - `GET /api/progress` → `{ "keys": [...] }`;
  - `PUT /api/progress/{section}/{topic}` → 204 (идемпотентно, `CompletedAt` не перезаписывается); `DELETE` того же пути → 204 (идемпотентно); неизвестная тема → 404;
  - `POST /api/progress/merge` с `{ "keys": [...] }` → объединение, ответ — полный набор `{ "keys": [...] }`; неизвестные/битые ключи молча отбрасываются (старый localStorage может хранить удалённые темы); больше 1000 ключей → 400;
  - `DELETE /api/progress` → 204, очищает весь прогресс пользователя («Сбросить»).
- CSRF: cookie-аутентификация + JSON, поэтому все изменяющие запросы требуют заголовок `RequestVerificationToken` (проверка `IAntiforgery` в фильтре эндпоинтов); токен для вошедшего пользователя рендерится в `<meta name="csrf-token">` в layout.
- Протокол клиента: слияние — **один раз на пару (браузер, пользователь)**. После успешного merge в localStorage пишется отметка `prog-checklist-merged:{userId}`; дальше при загрузке страницы сервер — источник правды (`GET` перезаписывает localStorage), клики отправляются `PUT`/`DELETE` оптимистично. Ошибка сети — галочка остаётся локально, при следующей загрузке выполняется повторный merge (отметка снимается при неудаче записи). Выход из аккаунта очищает localStorage (иначе прогресс одного пользователя «перетечёт» к следующему на этом же браузере).
- Гость — всё как раньше, только localStorage. Логика ключей (формат `"{section}/{topic}"`, проверка по каталогу, дедупликация) — в Core, работа с БД — сервис в Data.
Последствия: снятые галочки не воскресают; цена — офлайн-снятие галочки на устройстве, которое ещё не сливалось, при первом входе всё равно объединится (принимаем). Серверного рендера отмеченных тем нет — состояние рисует JS, как и раньше (SEO не затрагивается).
