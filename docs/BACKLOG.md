## P2 — Каркас контента

### P2-01 Модель и загрузка ресурсов — `done`
В Core: `Resource` (Title, Url, Kind, Lang, IsFree, IsAffiliate), enum'ы `ResourceKind` и `ResourceLanguage`, `IResourceCatalog.GetResources(sectionSlug, topicSlug)` → список (пустой, если нет). Реализация читает `content/resources.json` по ADR-11 и валидирует его против `ITopicCatalog`. Web: путь `Content:ResourcesPath`, файл копируется в output, singleton с загрузкой при старте. В репо — пустой `resources.json` (`"resources": {}`).
Приёмка: тесты на загрузку и на каждую ошибку валидации из ADR-11 (неизвестный ключ темы, пустой title, не-https URL, неизвестный kind/lang, дубликат URL в теме); порядок ресурсов сохраняется; приложение стартует с пустым файлом.

### P2-02 Уроки в Markdown — `done`
ADR-10: пакет `Markdig` в Core. `ILessonStore.FindLesson(sectionSlug, topicSlug)` → `Lesson?` (готовый HTML + первый абзац plain text для SEO). Загрузка всех `content/lessons/{s}/{t}.md` при старте, рендер один раз, `DisableHtml`. Ошибки старта: файл без темы в каталоге, `#`-заголовок первого уровня в уроке, пустой файл. Web: путь `Content:LessonsPath`, файлы копируются в output.
Приёмка: тесты рендера (заголовки, списки, код, таблица), сырой HTML в markdown выводится экранированным (`<script>` не проходит), все три ошибки валидации, отсутствие папки уроков = 0 уроков без ошибки.

### P2-03 Урок на странице темы — `done`
Если у темы есть урок — вместо блока «Урок в разработке» выводится HTML урока (стили типографики урока в site.css: заголовки, списки, `code`/`pre`, таблицы, цитаты — палитра прототипа, тёмная тема). Нет урока — заглушка как сейчас.
Приёмка: интеграционные тесты на фикстуре (тестовая папка уроков через конфиг): тема с уроком → HTML урока и нет заглушки; тема без урока → заглушка; HTML урока не экранирован дважды.

### P2-04 Блок «Где изучить» — `done`
На странице темы — секция «Где изучить» со списком ресурсов: название-ссылка, тип, язык, «бесплатно/платно». Внешние ссылки `rel="noopener"`, партнёрские — `rel="sponsored noopener"` + пометка «партнёрская ссылка» и строка-раскрытие под блоком. Нет ресурсов — секция не выводится.
Приёмка: интеграционные тесты на фикстуре ресурсов: порядок, атрибуты rel, пометка партнёрских, отсутствие секции без ресурсов; доступность (список `ul`, понятный текст ссылок).

### P2-05 Индикатор урока и SEO с контентом — `done`
В чеклисте (главная, раздел) у тем с уроком — бейдж «урок» рядом с уровнем. Meta description темы с уроком строится из первого абзаца урока (≤ 160, через `SeoText.Truncate`); без урока — как сейчас.
Приёмка: тесты: бейдж есть только у тем с уроком; description темы с уроком взят из урока; уникальность title/description по всем 269 страницам сохраняется.

### P2-06 Руководство для авторов контента — `done`
`docs/CONTENT.md`: как добавить урок и ресурсы, правила (заголовки с `##`, без сырого HTML, только https, без трекинг-параметров, политика партнёрских ссылок), пример урока и записи ресурсов, как проверить (тесты/WSL-скрипт). Строка в `docs/CONTEXT_MAP.md`.
Приёмка: пример из руководства, положенный в `content/`, проходит валидацию (тест или ручная проверка в описании коммита).

### P2-07 Пилотный контент — `done`
Уроки для 3 тем (`git/init-add-commit`, `databases/join`, `fundamentals/binary-bits-bytes`) и 2–4 ресурса для 10 тем. Ресурсы — только официальная документация и известные бесплатные источники (learn.microsoft.com, developer.mozilla.org, git-scm.com, postgresql.org и т. п.), без партнёрских ссылок.
Приёмка: валидация проходит; каждый урок ≥ 300 слов, фактически корректен (ревью); список всех URL — в описании коммита для проверки человеком.

## P3 — Аккаунты

### P3-01 Проект Data, модель и тестовая БД — `todo`
По ADR-12: проект `ProgChecklist.Data` (в `.sln`, ссылки Core ← Data ← Web), `AppUser : IdentityUser`, `AppDbContext : IdentityDbContext<AppUser>` с `UserTopicProgress` (PK, FK с каскадом, длина ключа). `AddAppDatabase(configuration)` в Web: Npgsql, пустая `ConnectionStrings:Default` → `InvalidOperationException` при старте, `Database:MigrateOnStartup`. Приёмка: все прежние тесты зелёные; тесты: модель на SQLite (сохранение/чтение прогресса, дубликат PK → ошибка, удаление пользователя удаляет его прогресс); старт без строки подключения → понятная ошибка; миграция в репо и `dotnet ef migrations has-pending-model-changes` (или эквивалент) не находит расхождений.

### P3-03 Identity и регистрация — `todo`
По ADR-13: настройка Identity (политика пароля, блокировка, cookie, 401 для `/api/*`), `UseAuthentication/UseAuthorization`. Страница `/account/register` (email, пароль, повтор) в стиле сайта, ошибки валидации по-русски, после успеха — вход и редирект на локальный `returnUrl` или `/`. `noindex`, нет в sitemap.
Приёмка: интеграционные тесты: GET 200 с antiforgery-полем; успешная регистрация ставит auth-cookie и редиректит; занятый email, короткий пароль, несовпадение паролей → 200 с текстом ошибки, пользователь не создан; POST без antiforgery → 400; внешний `returnUrl` → редирект на `/`; sitemap без `/account`.

### P3-04 Вход, выход и шапка — `todo`
`/account/login` (email, пароль, «Запомнить меня»), `/account/logout` (только POST с antiforgery). В шапке layout: гость — «Войти»/«Регистрация», вошедший — email и кнопка «Выйти». Блокировка после 5 неудачных попыток с понятным сообщением (без раскрытия, существует ли email).
Приёмка: тесты: верный пароль → cookie + редирект на локальный `returnUrl`; неверный пароль и неизвестный email → одинаковое сообщение; 6-я попытка после 5 неудачных → сообщение о блокировке даже с верным паролем; GET `/account/logout` не выходит; POST выходит; шапка различается для гостя и вошедшего; публичные страницы (главная, раздел, тема) для гостя не изменились (прежние тесты зелёные).

### P3-05 Сервис прогресса — `todo`

Data: `IProgressService` — `GetKeys`, `Mark` (идемпотентно, `CompletedAt` не перезаписывается), `Unmark`, `Clear`, `Merge` (объединение, возвращает полный набор), лимит 1000 ключей на merge.
Приёмка: юнит-тесты Core на разбор ключей (верный, неизвестная тема, лишние `/`, пустой, регистр — ординально); тесты сервиса на SQLite: идемпотентность Mark/Unmark, Merge = объединение без дублей, неизвестные ключи отброшены, лимит, изоляция пользователей (Clear одного не трогает другого).

### P3-06 API прогресса — `todo`
По ADR-14: эндпоинты `/api/progress` (GET, PUT/DELETE темы, POST merge, DELETE всего) с `RequireAuthorization`, проверкой antiforgery-заголовка для изменяющих запросов, `noindex`/не в sitemap. Layout для вошедшего рендерит `<meta name="csrf-token">` и `data-user` (id пользователя) на `body`; для гостя — ничего.
Приёмка: интеграционные тесты: гость → 401 на все эндпоинты (не 302); без заголовка токена → 400; PUT/DELETE/merge/clear по контракту ADR-14 (коды, тело, идемпотентность); неизвестная тема → 404; merge > 1000 ключей → 400; пользователь A не видит и не меняет прогресс B; meta/data-атрибуты есть только у вошедшего.

### P3-07 Синхронизация в progress.js — `todo`
По протоколу ADR-14: для вошедшего — однократный merge на (браузер, пользователь), далее GET при загрузке и оптимистичные PUT/DELETE на клик, «Сбросить» вызывает `DELETE /api/progress`, при ошибке сети — откат к повторному merge; выход очищает localStorage. Для гостя поведение не меняется. Без новых библиотек.
Приёмка: ручной чеклист в описании коммита (гость; первый вход с локальным прогрессом → объединение; снятие галочки не воскресает на втором браузере; сброс; выход очищает; офлайн-клик), JS без ошибок в консоли; серверные тесты зелёные; контракт разметки progress.js из STATUS не сломан.
